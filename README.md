# Conference Room Booking API

API для управління конференц-залами: створення/редагування залів, пошук доступності,
бронювання з автоматичним розрахунком вартості за часовими поясами та бізнес-звітність.

Побудовано на **.NET 10 / ASP.NET Core** за принципами Clean Architecture та Clean Code
(Robert C. Martin) — з прицілом на масштабованість, безпеку та відмовостійкість, як і
вимагало технічне завдання.

## Бізнес-задача

Компанія здає в оренду конференц-зали. Клієнту потрібно:

1. Адміністратору — керувати каталогом залів (назва, місткість, базова погодинна ціна,
   набір додаткових послуг) і каталогом самих послуг (проєктор, Wi-Fi, звук тощо).
2. Клієнту — шукати вільні зали на потрібну дату/час/місткість і бачити орієнтовну ціну
   ще до бронювання.
3. Клієнту — бронювати зал з обраними послугами й одразу отримувати підтвердження з
   детальним розрахунком вартості.
4. Бізнесу — бачити звіти: виручку, завантаженість залів, популярність послуг.

Вартість оренди залежить від того, на яку годину доби припадає бронювання:

| Часовий пояс         | Час           | Коефіцієнт |
|-----------------------|----------------|------------|
| Ранкові години        | 06:00–09:00    | ×0.90 (знижка 10%) |
| Стандартні години      | 09:00–18:00    | ×1.00 |
| Пікові години          | 12:00–14:00    | ×1.15 (націнка 15%), має пріоритет над стандартними |
| Вечірні години         | 18:00–23:00    | ×0.80 (знижка 20%) |

Бронювання, що перетинає кілька поясів (наприклад, 10:00–14:00), розбивається на сегменти
і кожен тарифікується окремо — це найризикованіша частина бізнес-логіки, тому вона
максимально покрита юніт-тестами (`StandardPricingPolicyTests`).

## Архітектура

Чотиришарова Clean Architecture — залежності спрямовані всередину, до `Domain`:

```
ConferenceRoomApi.Api            → контролери, DI-композиція, Swagger, middleware
        ↓ залежить від
ConferenceRoomApi.Infrastructure → EF Core, репозиторії, звіти, seed, міграції
        ↓ залежить від
ConferenceRoomApi.Application    → use-cases (RoomsService, BookingsService, ...), DTO,
                                    інтерфейси репозиторіїв, валідатори
        ↓ залежить від
ConferenceRoomApi.Domain         → сутності, інваріанти, доменна логіка (нема залежностей!)
```

`Domain` не має жодної залежності від EF Core, ASP.NET чи будь-якої іншої інфраструктури —
його можна взяти і використати в консольному застосунку чи іншому UI без змін. Найважливіша
бізнес-логіка (розрахунок вартості, `StandardPricingPolicy`) — це чиста функція без
побічних ефектів, що робить її тривіальною для тестування.

`Application` визначає інтерфейси репозиторіїв (`IRoomRepository`, `IBookingRepository`, ...)
— `Infrastructure` лише реалізує їх (принцип інверсії залежностей). Use-case сервіси
(`RoomsService`, `BookingsService`, `AdditionalServicesService`) — це конкретні класи без
власних інтерфейсів: вони самі є тим рівнем абстракції, яким користується `Api`.

## Ключові технічні рішення

### 1. Розрахунок вартості (`StandardPricingPolicy`)

Бронювання розбивається на межах часових поясів (06:00, 09:00, 12:00, 14:00, 18:00, 23:00),
кожен сегмент тарифікується окремо своїм коефіцієнтом, результати підсумовуються. Приклад
із самого ТЗ (Зал А, 10:00–14:00, база 2000₴/год) дає точний результат **8600₴**
(2×2000 стандарт + 2×2300 пік) — покрито тестом `Calculate_SpanningStandardPeakStandard_...`.

Правило пріоритету "пікові години виграють у стандартних при перетині" винесено в
`RateZoneCatalog.PriorityOrder`, а не захардкожене в умовах — зміна тарифів чи годин
роботи означає редагування одного списку, а не логіки алгоритму.

### 2. Захист від подвійного бронювання — у два рівні

- **Рівень застосунку**: перед створенням бронювання `BookingsService` перевіряє наявні
  підтверджені бронювання цього залу на цю дату (`Booking.OverlapsWith`) — дає користувачу
  зрозумілу помилку `409 Conflict` без зайвого походу до БД під навантаженням.
- **Рівень бази даних**: `EXCLUDE USING gist` constraint на `bookings` (міграція
  `AddBookingOverlapExclusionConstraint`) — гарантія на рівні PostgreSQL, що не залежить
  від коду застосунку. Це страхує від race condition, коли два запити одночасно проходять
  перевірку на рівні застосунку (класична проблема check-then-act) — виграє лише один
  `INSERT`, другий отримує помилку БД, яку `GlobalExceptionHandler` перетворює назад у
  зрозумілий `409 Conflict`.

Це продемонстровано інтеграційним тестом, що навмисно намагається забронювати
перетинний слот і очікує `409`.

### 3. Цінові снепшоти — для коректної звітності

`Booking` зберігає власний, "заморожений" на момент бронювання розклад цін
(`BookedPriceSegment`) і назви/ціни обраних послуг (`BookedService`), а не посилання на
поточну ціну залу чи послуги. Це означає, що зміна базової ціни залу завтра не змінить
задним числом виручку за вчорашні бронювання у звітах — критично важливо для будь-якої
фінансової звітності.

### 4. М'яке видалення (soft delete)

Видалення залу чи послуги не стирає рядок з БД (`IsActive = false`), а виключає його з
пошуку/списків. Історичні бронювання залишаються коректними — назва залу й ціни в них не
"ламаються", якщо зал згодом прибрали з каталогу.

### 5. Безпека

- **Валідація вхідних даних**: FluentValidation через глобальний `ValidationActionFilter`
  — жоден контролер не може "забути" провалідувати вхід.
- **Обробка помилок**: єдиний `GlobalExceptionHandler` повертає RFC 7807 `ProblemDetails`,
  ніколи не "світить" stack trace чи деталі підключення до БД клієнту; усе логується.
- **Rate limiting**: вбудований `Microsoft.AspNetCore.RateLimiting`, fixed window на IP
  (за замовчуванням 100 запитів/60с, конфігурується).
- **API-key guard** (`ApiKeyMiddleware`): опціональна перевірка заголовка `X-Api-Key` на
  запитах, що змінюють стан (`POST`/`PUT`/`PATCH`/`DELETE`). Вимкнена, доки в конфігурації
  `Security:ApiKeys` порожній — зручно для локальної розробки й оцінювання, вмикається
  додаванням ключів у продакшн-конфіг. Це прагматичний захист рівня "сервіс-сервіс", а не
  заміна повноцінної автентифікації користувачів — за потреби система росте до OAuth2/JWT,
  не змінюючи бізнес-логіку.
- **HTTP-заголовки безпеки** (`X-Content-Type-Options`, `X-Frame-Options`,
  `Referrer-Policy`), HSTS у production, явний CORS whitelist через конфіг.
- **SQL-ін'єкції**: неможливі — увесь доступ до даних через EF Core з параметризованими
  запитами, жодного конкатенованого SQL.

### 6. Звіти для бізнесу (`/api/reports/*`)

- `revenue` — виручка за період, з групуванням по днях або по залах.
- `room-utilization` — завантаженість кожного залу (заброньовані години / доступні
  години) — показує, які зали простоюють, а які варто розширювати.
- `popular-services` — які додаткові послуги замовляють найчастіше і скільки вони
  приносять доходу.
- `summary` — дашборд: кількість бронювань, скасувань, середній чек, найпопулярніший
  зал, розподіл виручки за тарифними поясами (скільки бізнес заробляє саме на
  "пікових" надбавках).

## Запуск проєкту

### Варіант 1 — Docker Compose (найпростіше)

```bash
docker compose up --build
```

Піднімає PostgreSQL і саму API; при старті застосунок автоматично застосовує міграції та
завантажує стартові дані (зали А/B/C, послуги з ТЗ). Swagger UI:
**http://localhost:8080/swagger**.

### Варіант 2 — локально (.NET SDK 10 + PostgreSQL)

```bash
# 1. Створити базу (якщо своя інсталяція Postgres, а не Docker)
createdb conference_rooms_dev

# 2. Застосувати міграції
dotnet tool install --global dotnet-ef
dotnet ef database update \
  --project src/ConferenceRoomApi.Infrastructure \
  --startup-project src/ConferenceRoomApi.Infrastructure

# 3. Запустити API
dotnet run --project src/ConferenceRoomApi.Api
```

Рядок підключення — у `src/ConferenceRoomApi.Api/appsettings.Development.json`
(`ConnectionStrings:Default`), за потреби перевизначте його змінною середовища
`ConnectionStrings__Default`.

## API

Повна інтерактивна документація — у Swagger UI (`/swagger`) одразу після запуску.
Основні ендпоінти:

| Метод | Шлях | Опис |
|---|---|---|
| `GET` | `/api/rooms` | Список залів |
| `GET` | `/api/rooms/{id}` | Зал за id |
| `GET` | `/api/rooms/available` | Пошук вільних залів на дату/час/місткість, з ціновою оцінкою |
| `POST` | `/api/rooms` | Створити зал |
| `PUT` | `/api/rooms/{id}` | Оновити зал (у т.ч. набір послуг) |
| `DELETE` | `/api/rooms/{id}` | Видалити зал (м'яко) |
| `GET` | `/api/additional-services` | Каталог додаткових послуг |
| `POST` | `/api/additional-services` | Додати послугу |
| `PUT` \| `DELETE` | `/api/additional-services/{id}` | Оновити / прибрати послугу |
| `POST` | `/api/bookings` | Забронювати зал — повертає повний розрахунок вартості |
| `GET` | `/api/bookings/{id}` \| `/api/bookings` | Бронювання за id / список з фільтрами |
| `DELETE` | `/api/bookings/{id}` | Скасувати бронювання |
| `GET` | `/api/reports/revenue` \| `/room-utilization` \| `/popular-services` \| `/summary` | Звіти |
| `GET` | `/health` | Health check (перевіряє з'єднання з БД) |

Приклад бронювання, що повторює приклад із самого ТЗ:

```bash
curl -X POST http://localhost:8080/api/bookings \
  -H "Content-Type: application/json" \
  -d '{
    "roomId": "<id Залу А>",
    "date": "2026-09-10",
    "startTime": "10:00",
    "endTime": "14:00",
    "additionalServiceIds": []
  }'
# → totalCost: 8600 (2×2000 стандарт + 2×2300 пік)
```

## Тестування

```bash
dotnet test ConferenceRoomApi.slnx
```

- **`ConferenceRoomApi.UnitTests`** — доменна логіка без жодної залежності від БД/мережі:
  усі граничні випадки розрахунку вартості (перетин поясів, точні межі, некоректні
  години) та інваріанти сутності `Booking`.
- **`ConferenceRoomApi.IntegrationTests`** — повний HTTP-стек (`WebApplicationFactory`)
  проти **справжнього** PostgreSQL (не in-memory провайдера — сенс цих тестів саме в
  перевірці реальних EF Core-мапінгів і `EXCLUDE`-constraint), окрема база
  `conference_rooms_test`. Перед кожним тестом дані бронювань/залів очищуються, каталог
  послуг заповнюється один раз.

CI (`.github/workflows/ci.yml`) піднімає Postgres-сервіс і виконує повний прогін тестів
на кожен push/PR.

## Можливі напрямки розвитку

Свідомо залишено поза обсягом тестового завдання, але природні наступні кроки для
масштабування продакшн-системи:

- Повноцінна автентифікація/авторизація користувачів (OAuth2/JWT) замість службового
  API-ключа — коли з'явиться поняття "клієнт" і "адміністратор" як окремі ролі.
- Оплата бронювань (інтеграція з платіжним провайдером) — зараз система лише рахує
  вартість, сам платіж поза обсягом ТЗ.
- Кешування каталогу залів/послуг (Redis) — при суттєвому зростанні навантаження на
  пошук доступності.
- Idempotency-key на `POST /bookings` для безпечних повторних запитів при таймаутах мережі.
- Багатомовність контенту (назви залів/послуг) — зараз одна мова.
- Підтримка кількох локацій/часових поясів одночасно (зараз одна бізнес-timezone,
  конфігурована через `Business:TimeZoneId`).
